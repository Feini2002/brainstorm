## 6. 本轮修复的真实缺陷

### 缺陷 1（本轮，阻断级）：重复查询参数被后一个值覆盖，多选材料核对永远只看到一个 id

- **现象**：`/api/selection?itemId=A&itemId=B` 只解析出 `B`。T062 的 e2e 五条用例全部
  卡在「材料核对面板不出现」，服务端日志为 `api selection.preview VALIDATION`。
- **根因**（两处叠加，都必须修）：
  1. `src/server/http/routeHandler.ts` 的 `parseQuery` 用
     `for (const [key, value] of url.searchParams.entries()) raw[key] = value;` —— 重复参数
     逐项赋值，后者**覆盖**前者。而 `SelectionQuery.itemId` 在契约里就是重复参数形态。
  2. `src/domain/schemas/http.ts` 的 `selectionQuerySchema.itemId` 是
     `z.array(uuidSchema).optional()`，但一个 query string 只能给出字符串，所以**单值形态也
     必然 400**——`/api/selection?itemId=<一个 id>` 从来没能工作过。
- **后果**（用户可见，不只是显示少一条）：
  - 材料核对面板描述的集合比用户勾选的**小**，且一条被删除的来源可能正好落在被截掉的
    位置上，于是 T062-C05「先阻止并要求确认新集合」根本没有机会触发——静默用更少的材料生成。
  - 显式 id 的选择预览实际不可用，只能靠标签筛选，这让"已删除记录"的检查在显式选择下不可达。
- **修复**：
  - `parseQuery` 收集重复参数为数组（保持首次出现顺序）；标量 schema 遇到重复参数现在会
    得到明确的 400，而不是静默截断。
  - `itemId` 改为接受「单个或数组」并**始终归一化为数组**，两种写法都是同一个请求。
  - 客户端 `apiClient.buildUrl` 支持数组值序列化为重复参数（`URLSearchParams.append`），
    否则浏览器侧无法表达这个契约形态。
- **回归**：`tests/integration/flow-material-confirm.test.ts` 两个用例（`T062-C05` 重复参数
  全部生效 + 删除后被逐个点名；`T062-C02` 单值形态仍是标量语义）通过；
  `tests/unit/session-client.test.ts` 等既有客户端套件在全量跑里通过。

### 缺陷 2（本轮）：空意图在归一化后残留空白，同一问题会被算成新工作

- **现象**：`tests/unit/flow-intent.test.ts` 的确定性断言失败：
  `normalizeFlowIntent(' 观察   顺序 \r\n\n\n\n 与依赖  ')` 得到 `'观察 顺序 \n\n 与依赖'`
  而不是 `'观察 顺序\n\n与依赖'`。
- **后果**：意图文本是 `sourceInputHash` 的输入之一。换行两侧的残留空格会让「同一个问题」
  在哈希上看起来是新的，于是重放不再命中——会多花一次模型调用，并且让"相同请求不重复付费"
  的保证在文本层被绕过。
- **修复**：归一化顺序改为 CRLF → 控制字符 → 水平空白折叠 → **去除贴行的空格**
  （`/ *\n */`）→ 折叠多余空行 → trim。
- **回归**：`T062-C02` 归一化用例通过（同一输入两次结果相同，且等于期望文本）。

### 缺陷 3（本轮测试自身的缺陷，记录以免被误读为产品缺陷）

- `T062-C04` 最初用 `{ ...lr, direction: null }` 做"除方向外相同"的比较。这个写法自己就
  改变了被比较的对象，第一次运行必然失败。
- 更重要的是随后暴露出一个**设计事实**：`requestKey` 按每次显式点击新生成（双击是一次请求，
  失败后重试是新的一次），所以两个方向的请求体在 `requestKey` 上**本来就不同**。断言改为
  「去掉 `direction` 与 `requestKey` 后整体相等」并**反过来断言** `requestKey` 两次不同——
  后者才是"改方向被当成新请求而不是重放"的证据。
- 另：`T062-C02/C03` 最初用 `traffic` fixture 的记账数组数请求，实测得到
  `Received length: 0`（该数组在 `page.route` 处理器里 push，相对测试进程的请求事件是异步的，
  "点击后立刻数"可能读到 0）。改为在用例开始时注册 `page.on('request')` 记账——它在请求发出时
  同步分发，一定先于 `waitForRequest` 看到同一个请求；`traffic` fixture 继续负责它的本职
  （阻断并记录 external host）。

### 缺陷 4（非本轮引入，但本轮为解除构建阻塞而修）

- `tests/integration/flow-history.test.ts:437` 连续两次调用 `getView(db, viewId)`，
  TypeScript 无法把 `kind === 'flow'` 的收窄传播到第二个表达式，报

  **如果并发写入者随后重写这段，本次修复可能被覆盖，请以其版本为准重新跑构建。**

### 10.1 `E2E_NO_BUILD`：Playwright 无法启动（环境阻塞，非断言失败）

> **⚠️ 本节结论已作废**，见第 11 节：工程随后产出了生产构建，守卫通过，三个页面层 spec

### 10.3 本轮修掉的真实缺陷（三个，都不是测试写法问题）

**缺陷 A（安全 + 可用性，阻断级）：只读谓词对「正文里的关键词」误报，导致整图打不开**

- 现象：`tests/browser/flow-render-security.test.ts` 的 T065-C01 整链用例红：
  `Error: 渲染结果没有通过安全净化：包含 javascript: 协议`。
- 根因：`findUnsafeSvgMarkup` 用 `/javascript\s*:/u` 扫**整段文档文本**。一条笔记只要在正文里
  写「见 javascript:alert(1) 这段」，渲染后那段话进入 `<text>`，谓词就判它不安全；而
  `renderFlowSvg` 在校验失败时**失败关闭**（throw），于是整张图打不开。
  这就是把安全规则实现成「谁提到就拒绝谁」。
- 影响（用户可见）：任何讨论 `javascript:`、URL、`<script>` 的笔记都会让它所在的流程图
  完全无法渲染——恰好是这类工具的常见材料。
- 修复：`findUnsafeSvgMarkup` 改为**结构化解析**：只读 `href`/`xlink:href`/`src` 等引用属性的
  **值**、`url(…)`/`@import`、`<style>` 内容、SMIL 写引用属性、禁止标签名与 `on*` 属性名。
  正文不再参与协议扫描。同时把「无协议的相对 `url(x.svg#p)`」也纳入拒绝
  （Mermaid 只发 `url(#…)`，拒绝它不损失画面，且让「不再产生请求」不依赖域名知识）。
- 回归：`tests/unit/flow-sanitize.test.ts` 的判据用例（两侧边界都钉住）、
  `tests/browser/flow-render-security.test.ts` 的「反向约束」与「只读谓词」两条用例。

**缺陷 B（安全，实测外发请求）：`USE_PROFILES` 覆盖白名单，`url(…)` 与 `@import` 真的外发**

- 现象：净化后的字符串里 `<use>`、`<a>`、`<image>`、`<style>`、`foreignObject` 全部存活；
  把净化结果按产品方式（`innerHTML`）放进活页面后，`marker-end="url(http://evil.example/m.svg#m)"`
  与 `<style>@import url("http://evil.example/x.css")</style>` 产生了**真实请求**。
- 根因两条：DOMPurify 的 `USE_PROFILES` 会在 `ALLOWED_TAGS`/`ALLOWED_ATTR` **之后**重建这两个集合，
  使显式白名单静默失效；且 `url(…)` 是函数记号而不是 URI 属性，DOMPurify 的协议检查从不看里面的地址。
- 修复：在 `ensureHooks` 里加两个钩子——`uponSanitizeAttribute` 拒绝 `on*` 前缀、重查引用属性、
  拒绝值里的远程 `url(…)`；`uponSanitizeElement` 在 `<style>` 含 `@import` 或远程 `url()` 时
  **清空其内容而不是删除元素**（Mermaid 的配色/虚线动画靠这块 CSS，删元素会改变画面）。
- 回归：`tests/browser/flow-render-security.test.ts` 的净化矩阵——每条攻击面逐个断言剥除，
  并且**逐条把净化结果插入活页面数真实请求**（26 条，全部 0 请求）。
- 说明：模块注释已按实测事实改写，明确「这两个数组是意图声明，钩子与移除检查才是执行点」。

**缺陷 C（T066-C04 相关，真实渲染循环）：`ref` 回调身份不稳定，`ResizeObserver` 每次渲染重新订阅**

- 现象：`MermaidRenderer.tsx` 把 `ref` 写成内联箭头函数 `ref={(element) => render.observeSize(element)}`。
- 根因：内联箭头函数**每次渲染都是新身份**，React 因此在每次渲染后先以 `null` 再以元素调用它；
  `observeSize` 的 `useCallback` 是稳定的，但它每次都 `disconnect()` 再 `observe(element)`，
  而 `ResizeObserver.observe()` **会立即投递一次回调**；回调里 `setSize({width, height})`
  写入**新对象身份**，`useState` 判定为变化 → 再渲染一次 → 再订阅一次 → 无限循环。
- 影响：一次尺寸变化会被放大成持续的渲染-订阅循环，正是 T066-R04「尺寸变化不重新渲染」
  要排除的行为。
- 修复（两处最小改动）：
  1. `useMermaidRender` 的回调改为**只在数值真的变化时**写入
     （`previous.width === next.width && previous.height === next.height ? previous : next`）；
  2. `MermaidRenderer` 的 `ref` 改为稳定的 `useCallback` 包装（在组件内用 `useCallback` 固定）。
- 诚实说明：**这条缺陷的回归断言在 `tests/e2e/flow-lifecycle.spec.ts` 的 T066-C04 里，
  本轮未执行**（10.1）。所以本轮对缺陷 C 的证明只有：源码层面的根因分析 +
  `npx eslint`/`tsc` 通过 + 该 spec 能被收集。**它的端到端验证是欠着的。**

### 11.3 T066 两条用例失败的根因：夹具装错了位置（**不是产品缺陷**）

第一次运行 `flow-lifecycle.spec.ts`，C03（重试不计费）与 C05（文本降级）红，现象一致：

1. 夹具 `page.evaluate(() => window.__feiniForceFlowRenderFailure = true)` 在 `openFlowPage`

改后 7/7 通过。**产品行为是对的**，错的是夹具的放置位置。

## 12. 第四轮：把 11.5 的「可读性取舍」真正修掉（编译期转义表 v3）

第 11.5 节记了一条**已知表现**：屏幕上的 `&#60;` 是编码后的尖括号，读作 `&#60;` 而不是 `<`，
当时明确写「本轮不声称它已解决」。本节把它修掉，并给出**改前 / 改后**都能复现的实测。

### 12.1 缺陷复现（改前）

诊断脚本直接从真实页面的 `svg text` 读屏幕文字（脚本用完即删）：

```
材料标签   （第一版）# 和 &
屏幕文字   &#40;第一版&#41;&#35; 和 &amp;
```

即：`compileFlow` 的旧 `LABEL_ENTITIES` 把 `()#[]{}|&` 全部写成数字实体，
而 Mermaid 在本仓库锁定的版本上对这类**缺 `&` 前缀**的数字实体**不做解码**，
于是用户看到的是 `&#40;` 这种死文本，不是 `(`。这不只是难看：`T064-C02` 的用例原文
要求标签**可辨认**，旧实现直接违反了它。

同轮还复现了第二个缺陷：标签里出现 `direction TB` 时，节点会**消失**并顺带把整图方向改掉
（关键词在引号内仍被当成指令）。

### 12.2 四轮真实 Chromium 探针的结论（决定新转义表）

| 输入形式 | 屏幕实际显示 | 结论 |
| --- | --- | --- |
| `&lt;` / `&gt;` / `&amp;` | `<` / `>` / `&` | **可解码，用这三种** |
| `#60;` `&#60;` `#34;` `&quot;` | 原样文字 `&#60;` 之类 | 死文本，全部弃用 |
| `\"` | 不能穿过 lexer | 弃用 |
| `( ) [ ] { } \| # ;` 与反斜杠 | 原样显示 | **原样安全，不需要转义** |
| 裸 `"` | 会在引号内提前闭合标签 | 必须处理，但**无可用实体** |

因此 `LABEL_ENTITIES` 收窄为四个映射：

```
&  → &amp;      <  → &lt;      >  → &gt;      "  → U+FF02（全角引号 ＂）
```

`()[]{}|#;` 与反斜杠**保持原样**，屏幕上就是用户写的字符。`"` 是唯一**有损**替换，
选择 U+FF02 而不是 `&quot;`：前者屏幕上是可读的 `＂`，后者是死文本。
这条损失在模块注释里标注为「the one unavoidable lossy substitution」，不藏着。

`direction` 关键词的修法：只在 `direction` 与合法方向之间插入一个零宽空格，
打断 lexer 的前瞻、不影响人读，且**不引入任何实体**（故不会被第二轮转义再编码）。

`FLOW_COMPILER_VERSION` 随之从 `v2` 升到 `flow-compiler-v3`。
