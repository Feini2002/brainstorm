## 8. 本轮修复的真实缺陷

每条都有可复现现象，不是风格偏好。复现方式与本节命令一致。

| 缺陷 | 后果 | 修复 |
| --- | --- | --- |
| `MindmapRenderer` 把 Markmap 实例挂在**外层 `<svg>` 上**，而该节点内含 React 渲染的内层 `<svg>` | Markmap 的首次 append 把自身 `<style>` 与根 `<g>` 追加到内层 svg 之后，`destroy()` 只删自己的子节点，内层 svg 被留下；`fit()` 量到 `0×0` 几何，写出 `translate(NaN,NaN) scale(NaN)`。节点全部存在于 DOM 却零面积不可见 —— 这正是 `toBeVisible()` 间歇失败的原因，且失败的是一张**看似已绘制完成**的图 | 画布即为被交给 Markmap 的那一个 `<svg>`（`ref` 直接落在它上面），React 不在其中渲染任何子节点；挂载前不再把 svg 包进额外 `hidden` 容器（`display:none` 同样会让 `fit()` 量到零几何并以 NaN 变换写回） |
| `annotateTree` 只接受"渲染节点数 === id 数"一种形态 | 标题与根节点**同名**时 Markmap 的根就是 AST 根，而旧实现把根从 id 列表里省掉，于是渲染器把 Markmap 的根和第一个子节点配成一对：点节点会打开**另一个节点**的来源，并且每一张"根与标题同名"的正常脑图都被判为结构不一致而拒绝绘制 | `annotateTree` 用节点数区分两种形态：同名时逐位置对齐；不同名时 Markmap 的根是标题合成的、不对应任何 AST 节点（恰好多 1 个），该节点保持无 id 以免 `byId` 出现两个同 id 节点 |
| 大纲在结构异常时**沿用正常遍历并只补上"走不到的"节点** | 重复 id 会让遍历第二次遇到该 id 时永久跳过，一张 3 节点的坏图只显示 2 行——恰好丢掉了"哪一行是重复的"这个信息 | 结构检查不合格时整体改用扁平列表，逐行列出存储中的每个节点（`buildOutlineRows`） |
| G4 里额外加了 `FIT_DEADLINE_MS` 竞速与"挂载超时"兜底 | 这两者都是为**上面那条真实根因**发明的第二套机制；根因去掉后 `fit()` 在 18–70ms 内必定落定，兜底成了不会触发的死代码 | 撤掉 `FIT_DEADLINE_MS`；保留一个 15s 的挂载超时（`setData` 不落定时本来**没有任何**可观察信号：无错误、无 reject、无失败请求），且仅当 live handle 仍在时触发 |
| `computeStaleness` 把**已删除的关系 id 塞进 `missingSources`** | 该字段的契约是「已不存在的**条目** ID 数组」，调用方按条目 id 去解析标题——关系 id 混进去会解析失败，界面只能把它们当成"找不到的笔记"显示，而真实原因（这条关系没了）丢失 | `missingSources` 只收条目 id；关系缺失照常计入 `changedRelationIds` 并在新增的 `drift` 明细里带 `kind: 'relation'`；`describeStaleness` 对已删关系单独成句 |
| 生成接口只接受 `selection.mode='explicit'`，而按标签保存的视图存的是 `filter` | 这类视图在过期后无法重新生成：界面拿不到"当前选择解析成哪些 id"，只能报错或静默发出一个不含材料的请求 | `getViewFreshness` 用与生成路径**同一个** `captureSources` 重新解析存储的选择，把 `resolvedIds` 交给确认框；确认后由界面按既有契约发 `{mode:'explicit', itemIds}`，服务端不接受筛选体这一点没有放宽 |
| 客户端组件从 `@/server/services/...` 取 `ViewFreshness` 类型 | 违反 T003-R02（浏览器侧不能引用服务端运行时模块），lint 直接报错；即使绕过得去，客户端 bundle 也会把服务端模块拖进来 | 读模型类型移到 `src/domain/view.ts`，与 `RunDiagnostics` 放在域层的既有做法一致；服务层 `export type { ViewFreshness }` 转出，两侧共用一个名字 |

复现根因（修复前）：在真实浏览器里往返 8 轮打开同一张已保存脑图，统计 `g.markmap-node`、
`<style>`、根 `<g>` 的 transform 与渲染器文案。修复前可稳定观察到
`{"nodes":0,"styles":0,"gs":0,"cls":"h-full w-full cursor-grab",...}` 或
`{"nodes":2,"styles":1,"gCount":4,"transform":"translate(NaN,NaN) scale(NaN)"}` 且文案仍是「正在渲染脑图…」。
修复后同一探针 8 轮全部为 `18–70ms` 内挂载完成、无 console 错误。

## 9. 本 Gate 的共享模块扩展

`src/server/llm/transport.ts` 新增的 `BRAIN_SCRIPTED_PROVIDER` 缝是**跨任务**修改，集中记在这里
（本节不只是 T061 的局部改动）：

- **为什么需要**：T061-C01/C03/C04 必须走**生产的生成路径**（真实路由、适配器、结构校验、
  事务落库），否则"闭环"无从谈起；但 `endpointPolicy` 禁止 loopback HTTP，浏览器用例无法把真实
  适配器指向本地桩。该缝因此只把**出站 HTTP 一步**换成脚本回复，其余全真跑。
- **受影响任务**：T055、T056、T058、T059、T060（生成与渲染路径），以及 T061 本身。
- **默认关闭**：环境变量未设置时仍是真实 `FetchTransport`，生产路径零行为变化；设置了也要求
  **非用户数据目录**，否则直接抛错。
- **回归结论**：本次完整重跑 `npm test` **450/450 通过**（含 `tests/unit/scripted-provider.test.ts` 8 例）；
  全量 e2e `npx playwright test` **79/79 通过**（13 个 spec），其中 G4 相关 `gate4.spec.ts` 6 例、
