## 7. 本轮修复的真实缺陷（T013–T021 补测过程中发现）

四处都是「守卫缺失 / 形状判定缺失」导致的真实后果，不是为了让测试通过而改实现。
每处都给出变异验证（删掉修复后测试会失败）。

### 7.1 T016｜搜索不覆盖标签名

- **现象**：`listItems` 的 `q` 条件只匹配 `title / summary / raw_text`。`T016-R01` 与
  `LibraryPage.tsx` 的搜索框提示都写明搜索覆盖标签名。
- **后果**：给一条记录打了「AI」标签后，在资料库搜「AI」查不到它 —— 用户以为标签没保存。
- **修复**：`src/server/repositories/items.ts` 的 `where` 增加
  `EXISTS (SELECT 1 FROM item_tags it JOIN tags t ON t.id = it.tag_id WHERE it.item_id = knowledge_items.id AND t.label LIKE ? ESCAPE '\')`。
- **回归**：`tests/integration/query-items.test.ts` 的 T016-C01 搜索用例；移除该 `EXISTS`
  子句后该用例失败。

### 7.2 T017｜标签数超过上限被静默截断

- **现象**：`validateUserPatch` 只检查 `patch.tags.length > LIMITS.tagsPerItem * 4`（原始数组
  的 4 倍上限，那是 wire schema 的粗筛）。规范化并去重后仍有 9 个不同标签的请求，服务端
  返回 200，`setItemTags` 静默丢掉第九个。
- **后果**：用户看到「保存成功」，但有标签没有落库，且没有任何提示。数据与界面不一致，
  用户无从发现。`docs/03_contracts/03_dto_and_version_rules.md §2` 与 `T017-C03` 都要求
  验证失败并提示。
- **修复**：`src/domain/itemFields.ts` 的 `validateUserPatch` 先做 `normalizeTagList` /
  `normalizeKeywordList`，再用 `droppedOverLimit` 判断，错误消息带上上限与「要减少几个」。
  关键词同源问题一并修复。
- **回归**：`tests/integration/tags.test.ts` 的 T017-C03 两组（服务层 + HTTP 层），以及
  T017-C03/R02「去重后恰好八个必须通过」的反面样本。把 `validateUserPatch` 改回只比较
  原始数组长度后，这两组失败。

### 7.3 T006｜畸形信封抛裸 `TypeError`

- **现象**：`apiClient.parseEnvelope` 只有 `body.ok === true` 一个判断，随后直接
  `throw new ApiClientError(body.error, ...)`。对端返回合法 JSON 但不是本项目信封时
  （占位网关的 `{"data":[]}`、门户的 `{"error":"…"}`、旧版本服务的形状），`body.error`
  是 `undefined`，构造函数读 `error.code` 抛
  `TypeError: Cannot read properties of undefined`。
- **后果**：统一信封的意义是「失败也有稳定形状」。这条路径下用户拿到的是未处理异常，
  界面无法显示可读原因，`requestId` 也丢了，无法与日志对齐。
- **修复**：`src/features/shared/apiClient.ts` 增加 `isSafeError` 形状判定与
  `failureFromBody` 回退；非本项目信封统一映射为「本地服务返回了无法识别的响应（HTTP xxx）」
  并保留 `x-request-id`。
- **回归**：`tests/unit/api-envelope.test.ts` 的 T006-C06 两组（`ok` 缺失、`ok:false` 但
