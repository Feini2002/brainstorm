## 4. 关键不变量与观察方式

### 付费动作的费用边界（T035）

用计数型替身（`tests/integration/helpers/`）观察，而不是靠日志推断：

| 场景 | 用例 | 观察结果 |
| --- | --- | --- |
| 未配置时发起整理 | `organize-service.test.ts#T036-R01` | 外部调用数 0；没有 Run 行；原文未变 |
| 同键成功重放 | `run-lock.test.ts#T035-R02` | 第二次调用返回既有结果，外部调用数仍为 1 |
| 同键失败重发 | `run-lock.test.ts#T035-C05` | 返回原失败，不再次扣费 |
| 忙碌时新操作 | `run-lock.test.ts#T035-R04` | 返回 `RUN_BUSY`，外部调用数 0，槽位未被占用 |
| 连接测试连点 | `connection-test.test.ts#T032-C06` | 同一 `requestKey` 只保留一次外部调用 |

### 事务切点（T036）

`organize-service.test.ts#T036-C02` 在模型请求**进行中**保存另一条笔记：因为请求期间不持有
事务，保存成功返回。`#T036-C04` 让标签写入失败，验证元数据、关系与 Run 成功标记**一起回滚**。

### 恢复与终态单向性（T040）

`run-recovery.test.ts#T040-C03`：先让恢复把运行标为 `interrupted`，再投递迟到的成功响应，
断言响应被丢弃且终态没有复活。`#T040-R05` 断言恢复本身不调用模型、也不删除 Run 行。

### 诊断的读时安全（T041）

- `#T041-C01` 用量缺失时返回「未记录」，且读取**不写库**；
- `#T041-C04` 断言响应体里没有秘密、没有原文，`endpointOrigin` 只到主机；
- `#T041-C05` 中断的运行给出计费说明（本机结束，不承诺对方未计费），且不因读取而复活；
- `#T041-C06` 显示实际候选数，不是契约上限 40。

### 秘密不进入日志与响应（T029/T030）

- `settings.test.ts#T029-C01`：GET 响应里没有 Key 的任何痕迹，未配置时不伪造
  `apiKeyConfigured`；
- `run-lock.test.ts#T035-C06`：持久化的 Run 行里没有 Key、`Authorization` 或完整请求正文；
- `redaction.test.ts`（14 例）：结构化白名单 + 值脱敏双层，含「服务商把 Key 回显在错误信息里」
  这一条。

## 5. 本轮 review 修复的真实缺陷（含复现入口）

### 5.1 e2e 测的是过期构建

**现象**：`npx playwright test` 报 `T024-C01 创建与检索不应触发任何模型调用` 失败，列出了 3 次
`POST /api/items/<id>/organize`。表面看是刚修完的离线路径回归。

**定位**：比较时间戳即可证伪：

```
.next/BUILD_ID            09/14/2026 22:10:05
src/features/inbox/CaptureBox.tsx   09/14/2026 22:10:41
```

构建比最后一次源码修改早 36 秒。`playwright.config.ts` 用的是 `next start`，服务的是 `.next`，
所以那次运行测的是**改之前**的应用。

**修复**：`tests/e2e/support/buildFreshness.ts`，在配置加载阶段（`webServer` 启动之前）比较
`.next/BUILD_ID` 与 `src/**`、`next.config.ts`、`package.json` 的最新 mtime。

用真实配置验证过守卫会触发（临时把一个源文件的 mtime 调到未来）：

```
$ npx playwright test --list
Error: E2E_STALE_BUILD: 生产构建比源码旧，e2e 会测到上一次构建的结果。
  构建时间：2026/9/14 22:20:20
  最新源码：src\components\AppShell.tsx（2026/9/14 22:28:18）
  请先运行 npm run build，再运行 npm run test:e2e。
```

恢复 mtime 后 `--list` 立即通过（18 tests / 3 files），守卫本身不产生误报。

**重跑结果**：`npm run build` 后再次 `npx playwright test` → **18 passed**，其中 `T024-C01` 通过。
这确认离线路径本身没有缺陷：`CaptureBox` 只在 `modelConfigured` 为真时才挂载 `organize`。

**判定**：这是**测试基础设施缺陷**，不是产品缺陷。4 个单元用例（`build-freshness.test.ts`）
把守卫行为固定下来，包括「嵌套目录里的改动同样算数」和「没有构建产物时不误报」。

### 5.2 Windows 文件锁让整个套件死在配置加载

**现象**：同一轮运行中 `T024-C02` 与 `T025-C01` 报

```
Error: EPERM, Permission denied: \\?\C:\...\tests\e2e\.data
    at resetE2eDataDir (tests\e2e\support\resetData.ts:28)
    at Object.<anonymous> (playwright.config.ts:34:16)
```

9 个用例因此 not run。

**定位**：上一进程刚被杀死时，Windows 仍可能短暂持有 SQLite 文件及其 `-wal`/`-shm`。这不是
权限问题，删更多文件没有用。

**修复**：`rmSync` 传 `maxRetries: 20, retryDelay: 250`（Node 自身重试 `EBUSY`/`EPERM`/
`ENOTEMPTY`），并在最终失败时报告具体目录、去掉理由与处置建议。

### 5.3 `.gitignore` 漏掉重启用例的数据目录

**现象**：`git check-ignore -v tests/e2e/.data-restart` 退出码 1（未忽略），而 `resetData.ts`
确认这个目录属于测试套件。跑完一次 e2e 后 `git add -A` 可能把 SQLite 数据库提交进仓库。

**修复**：加入 `/tests/e2e/.data-restart/`；同时把本地核验产生的 `/ .tmp-*.log` 与
`/.tmp-*-data/` 一并忽略。验证：

```
$ git check-ignore -v "tests/e2e/.data-restart/"
.gitignore:46:/tests/e2e/.data-restart/    tests/e2e/.data-restart/
```

### 5.4 配置注释指向不存在的脚本

`playwright.config.ts` 的注释写着「`scripts/prepare-e2e.mjs` resets」，但该文件并不存在，
实际执行者是 `tests/e2e/support/resetData.ts`。已改正。
