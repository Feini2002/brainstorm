## 3. 本 Gate 已通过的硬性约束

- **T057-R02 / T057-R03**：只使用 `markmap-lib/no-plugins` 入口，并在挂载时**断言**
  `getUsedAssets()` 为空——未来依赖升级若重新启用插件会直接报错而不是静默外联。净化只放行白名单
  标签与属性，`on*` 一律拒绝。
- **T057-R04**：实例与 SVG 都由 `ref` 持有；Strict Mode 的挂载→卸载→挂载往返 4 轮后
  `svg`/`svg.markmap`/`<style>` 仍各 1 个。
- **T057-R05**：`autoFit: false`，一次挂载只 fit 一次；选节点与容器尺寸变化都不改 transform。
- **T058-R01**：来源交互全部是本系统 React 列表，模型只提供 id，没有任何模型生成的 HTML 或链接。
- **T058-R02 / R03**：分组节点显示子树去重结果，同一 Item 多引用只出现一次，而树的引用关系保留。
- **T058-R05**：大纲与画布消费同一个 `content`，共享 `mindmapChildrenIndex`；折叠是本地视图状态，
  折叠/展开期间零 API 请求（已断言）。
- **T058-R06**：大纲控件是真实 `<button>`，`aria-expanded` / `aria-current` 反映状态，键盘可完成
  展开与打开来源。

- **T059-R01**：过期说明给出**具体**来源与版本变化（「原文 v1 → v2」「revision 1 → 2」），
  而不是笼统的「依据已过期」；`missingSources` 只含条目 id，关系缺失由 `drift` 带 `kind` 单独报告。
- **T059-R02 / R04**：重新生成产生新 View，旧 View 的 id / revision / name / content / contentHash /
  generatedAt 逐项不变；失败路径同样不动旧图（已在浏览器与集成两层断言）。
- **T059-R03 / R05**：过期报告是**只读**计算，读取前后视图四个字段逐项相等；筛选型选择在读取时
  重新解析并把 `resolvedIds` 交给用户确认，服务端仍然只接受显式 id 列表。
- **T059-R06**：来源全删后不提供生成入口，并断言此时没有发出任何生成请求；旧图仍可读并显示缺失来源。

- **T060-R01**：Markdown 由**已编译的规范 AST** 重新生成，不是缓存源或再次渲染；同一视图同日连导
  两次，除显式「导出时间」一行外逐字节相同。
- **T060-R02**：文件名不采信用户输入——只由 `viewId` 前 8 位与日期构成，视图名（可能含 `../`、
  `..\\`、`<script>`、`:`）一律不进文件名；`filename*` 按 UTF-8 百分号编码。
- **T060-R03**：JSON 导出含 `schemaVersion` / `kind` / `sourceSnapshot` / `content` / `freshness`，
  不含 Key、`Authorization` 或任何凭据；两份格式都在过期时显式标注生成依据与过期原因。
- **T060-R04**：导出是**只读**操作，前后 `content` / `contentHash` / `generatedAt` / `revision` /
  `selection` 逐项相等；不写 `generatedAt`、不建新视图。
- **T060-R05**：MVP 只提供 Markdown 与 JSON；`?format=pdf` 走 `VALIDATION` 失败信封，界面上
  没有任何无效格式入口。

## 4. 本轮修复的真实缺陷

三条都在证据文件第 5 节给出复现方式，其中第一条是**用户可见**的：
1. **画布几何损坏**：`MindmapRenderer` 把一个内含子节点的 `<svg>` 交给 Markmap，`destroy()`
   清不掉内层节点、`fit()` 量到零几何并写出 `scale(NaN)`，导致节点在 DOM 中但零面积不可见。
   表现为"图看起来画完了但什么都没有"。
2. **节点 id 与渲染位置错位**：根节点与标题同名时 id 列表漏掉位置 0，点一个节点会打开另一个
   节点的来源，且正常脑图被判为结构不一致而拒绝绘制。
3. **大纲丢节点**：结构异常时沿用正常遍历，重复 id 会让被吞掉的行永久消失。

第 1、2 条由 T057-C05/C06 与新增的回归断言钉住；第 3 条由 T058-C06 的"三行全部列出"钉住。

T059 另修了两条与契约字段直接相关的缺陷（同见证据第 5 节）：

4. **`missingSources` 混入关系 id**：该字段契约是「已不存在的条目 ID 数组」，调用方按条目 id
   解析。关系 id 混进去后会解析失败，界面只能显示成"找不到的笔记"，真实原因丢失。现在关系缺失
   由 `drift` 携带 `kind` 报告，`describeStaleness` 对已删关系单独成句。
5. **筛选型视图无法重新生成**：生成接口只接受显式 id 列表是契约要求（`04_api_contract.md` §38），
   但按标签保存的视图存的是 `filter`，界面因此拿不到"当前会发哪些 id"。现由 `getViewFreshness`
   用与生成路径同一个 `captureSources` 重新解析并交给确认框，服务端体格式没有放宽。

T060 未发现新的产品缺陷。唯一一次失败是**测试写得比契约更严**：T060-C05 原本要求两次导出逐字节
相同，而同一天连导两次时「导出时间」差了几毫秒。契约允许这一行不同，因此改成先归一化该行再比对
全文，而不是放宽产品实现。

## 4.1 T061 收口时修掉的问题

T061 本身不引入产品缺陷，但把四条**用例问题**查出来了（细节见证据文件第 8 节末表）：

1. **C02 数据目录错位**：视图种进 `.data`，却在 `.data-restart` 的服务上打开——与环境无关地必挂，
   且会被误读成"重启丢数据"。改为种进重启服务自己的目录。
2. **C02 死代码**：「重启后不再请求模型」原本只有一句没有断言的 `pages().length`，等于这条契约
   没有证据。改为对流量记账断言 `generate` 为 0、外网请求为 0。
3. **C04 选项未刷新**：直调生成 API 后页面下拉没有新视图 id，用例必挂且失败原因与"再生成另存"无关。
4. **C01 展开层级口径不符**：断言 5 个节点，而产品默认「两层」只画 4 个（62 次稳定复现）。
   根因是**产品行为正确**（三层树的深节点被设计性折叠），因此经产品自己的「全部展开」再断言全树，
   而不是为了迁就用例去删掉展开控制。
