## 一、结论

在没有真实 API Key 的条件下，本阶段交付了完整的「配置 → 连接测试 → 整理 → 落库 → 诊断」
链路，并且每个付费动作的费用边界都是可验证的：

- 未配置或配置不完整时**不产生任何 Run 行、不占用槽位、不发请求**（`assertConfigured` 在
  `configSnapshot` 之前，因为后者需要能解析的 endpoint）；
- 一次失败**不会被静默重试**（`paidAutomaticNetworkRetries = 0`）；重发必须带同一个
  `requestKey`，命中即复用既有结果或既有失败；
- 全局同时只允许**一个** running Run，由 `idx_one_global_running` 这个部分唯一索引保证，
  而不是进程内变量，所以两个浏览器标签页也无法各发起一次付费调用；
- 模型请求**不在事务里**：整理期间保存别的笔记、编辑别的条目、渲染页面都照常工作。

真实模型连接（需要用户自己的 Key）继续标为 **BLOCKED_BY_EXTERNAL_CREDENTIAL**。
本阶段的验证用记录请求/响应的替身完成结构断言，替身与真实调用在证据中分开标注。

## 四、规则落点（逐条）

- **T027-R02** Key 只从输入框经 `PUT /api/settings/llm` 进入秘密表；GET 只返回
  `apiKeyConfigured` 布尔，响应里没有 Key 的任何片段。
- **T028-R01/R02** 只接受 HTTPS、禁止用户名/密码、查询参数、片段与 `/chat/completions`
  自带路径；`localhost`、回环与内网字面量被拒绝。声明的边界：公网域名仍可能解析到内网地址，
  这一点写在模块注释里，不谎称已拦截。
- **T028-R03** 换 origin 而保留旧 Key 需要显式确认（`requiresKeyTransferConfirmation`）；
  仅改路径不需要。
- **T029-R01/R02** 配置与秘密在**同一个事务**里写；`revision` 用 CAS 保护，旧 revision 被拒。
- **T029-R03** 秘密写入失败时整次回滚，不会出现「新地址 + 旧 Key」；删除失败不误报已删除。
- **T030-R01/R02** 日志记录是白名单结构（没有 `data` / `body` / `headers` 字段），并且字符串
  再过一层值脱敏：先替换**当前活跃秘密的字面量**，再匹配 `sk-`/`Bearer` 等凭证形状。
- **T030-R04** 用户可见消息经 `stripAbsolutePaths` 去掉绝对路径；`keyLength` 字段恒为
  `null`（长度本身就是秘密的指纹）。
- **T031-R01** 从不发送 `temperature`；`max_tokens` 与 `max_completion_tokens` 至多出现一个。
- **T031-R02** 只有显式选择 `json_object` 才发 `response_format`；模式被服务商拒绝时如实报错，
  不偷偷换另一种模式重试。
- **T031-R03** 超时是**操作的绝对截止时刻**（`attemptTimeoutMs`），不是每次尝试重新计时，
  所以一次修复不会给自己续 45 秒。
- **T031-R04** 响应体按字节上限读取（`readBoundedBody`），非 2xx 与非 JSON 走不同分支。
- **T033-R01** 用户材料被包在 `<<<UNTRUSTED MATERIAL>>>` 之间，系统消息明确说明其中内容不得
  当作指令；注入样本见 `tests/fixtures/prompt-injection.json`。
- **T034-R02** `LIKE` 的 `%` 与 `_` 按字面转义，搜 `50%` 不会匹配全部。
- **T034-C06** 只做字面召回，不是语义检索；词不同就用 `notes` 承认局限，不假装语义命中。
- **T035-R02/R03** 同键重放返回既有结果且不执行；全局槽位由唯一索引占用。
- **T035-R04** 事务在发起网络请求**之前**提交；插入失败意味着外部调用数为 0。
- **T036-R02** 模型调用期间不持有事务，其他写入不被阻塞。
- **T036-R04** 元数据、标签、关系、条目状态、dataset revision 与 Run 终态在**一个事务**里一起
  提交；任一失败则整体回滚，原文不受影响。
- **T037-R02** 只用 `JSON.parse`，没有 `eval` / `Function` / YAML 加载器。
- **T037-R05** 修复只对「完整但格式不对」的答案开放，且只在操作预算内；截断、拒答、空输出是终态。
- **T038-R03** 整理期间 `rawVersion` 变化则整次拒绝，不做逐字段合并。
- **T039-R01** 引用本次未发送的条目按未知条目拒绝；证据 quote 必须是当前原文的子串。
- **T039-R03/R05** 同一批返回的重复 `(targetId, type)` 只写一条；仍为 `suggested` 的同键关系
  就地刷新，不插平行边。
- **T040-R01** 只恢复超过租约的行；未过期的运行保持 `running`。
- **T040-R03** 终态单向不可复活：恢复先发生则迟到响应被丢弃。
- **T040-R05** 恢复不调用模型、不删除 Run 行。
- **T041-R01/R02** 诊断读取是只读的：不触发模型、不新增 running 槽位、不写库。
- **T041-R05** 用量缺失时报告「未记录」，不用字数换算或默认值伪装；摘要中不出现金额或推算费用。

## 五、本轮 review 发现并修复的真实缺陷

第 41 项任务完成后做了一轮深度 review。以下每一条都有可复现的失败现象，不是风格偏好。

| 缺陷 | 后果 | 修复 |
| --- | --- | --- |
| e2e 运行的是**过期生产构建**（`CaptureBox.tsx` 22:10:41 被改，`.next/BUILD_ID` 写于 22:10:05） | `T024-C01` 报「创建触发了模型调用」，看起来像刚修完的离线路径回归，实际是构建比源码旧了 36 秒；这类误报会把真实回归淹没 | 新增 `tests/e2e/support/buildFreshness.ts`：在配置加载阶段比较 `.next/BUILD_ID` 与 `src/**`、`next.config.ts`、`package.json` 的最新 mtime，过期即 `E2E_STALE_BUILD` 并给出「先跑 npm run build」的处置；4 个单元用例（含嵌套目录与「无构建产物时不误报」） |
| `resetE2eDataDir` 在 Windows 上被上一进程残留的文件锁打断 | 一次 `EPERM` 让整个套件在**配置加载阶段**就死掉，9 个用例直接 not run，且错误信息只有一行 EPERM | `rmSync` 加 `maxRetries: 20, retryDelay: 250`（Node 自身重试 `EBUSY/EPERM/ENOTEMPTY`），并在最终失败时报告具体目录与原因 |
| `.gitignore` 只忽略 `tests/e2e/.data/`，没有 `.data-restart/` | 跑完一次 e2e 后 `git add -A` 可能把重启用例的 SQLite 数据库提交进仓库 | 两个目录都列入；同时把本地核验用的 `.tmp-*.log`、`.tmp-*-data/` 一并忽略 |
| `playwright.config.ts` 注释指向并不存在的 `scripts/prepare-e2e.mjs` | 文档与实现不一致，误导后续排查 | 注释改为指向真实的 `tests/e2e/support/resetData.ts` |

`T024-C01` 的修复结论：该用例当前**通过**，且离线路径本身没有问题——`CaptureBox` 只在
`modelConfigured` 为真时才挂载 `organize`，无 Key 时「保存并整理」只保存并给出提示。
