## 6. 本轮修复的真实缺陷（摘要）

完整的现象/根因/后果/修复/回归见证据文件第 6 节。前两条是本轮发现的**产品缺陷**：

1. **重复查询参数被覆盖 + 单值形态必然 400**：`/api/selection?itemId=A&itemId=B` 只解析出 `B`，
   且单值形态从来无法通过 schema。后果是材料核对面板描述的集合比用户勾选的**小**，
   被删除的来源可能正好落在被截掉的位置上，于是「先阻止并要求确认新集合」根本没有机会触发。
   修复：`parseQuery` 收集重复参数为数组；`itemId` 接受单值或数组并始终归一化为数组；
   客户端支持数组值序列化为重复参数。回归见 `tests/integration/flow-material-confirm.test.ts`。
2. **意图归一化残留贴行空格**：换行两侧空格让「同一个问题」的哈希看起来是新的，重放不再命中，
   会多花一次模型调用。修复：归一化顺序加入「去除贴行空格」。回归见 `T062-C02` 确定性用例。

第 3、4 条分别是本轮测试自身的写法缺陷，以及为解除构建阻塞而修的一行类型收窄（**非本轮引入**），
同样记在证据文件里，避免把它们误读成产品缺陷。

### 8.4 T066 两条用例的真实失败原因（**夹具装错了位置，不是产品缺陷**）

第一次运行 `flow-lifecycle.spec.ts` 时有两条红（C03 重试不计费、C05 文本降级），
现象都是「要求渲染失败，结果 `data-phase="ready"`」。根因是**夹具时序**：

- `page.evaluate` 设置 `__feiniForceFlowRenderFailure` 是在 `openFlowPage` **之后**执行的；
- 而 `/flow` 在挂载时会**自动采纳最新的一张已保存流程图**（`page.tsx` 的 mount effect），
  也就是说那一次渲染在夹具装好之前就已经成功完成了；
- 随后再 `selectOption(同一张图)` 并不会改变渲染副作用依赖的 `source`（编译出来的字符串相同），
  而 T066-R04 要求的正是「源没变就不重新渲染」——所以夹具永远没有被触发。

修法是改用 `page.addInitScript`，在任何页面脚本之前装上开关，于是挂载时那次渲染就是失败的那次。
改后 7/7 通过。**这不是产品缺陷**，是测试夹具的放置位置错了；同时说明产品行为是对的。

另外顺手收紧了两条**过弱的断言**：`flow-fallback` 是常驻的文本替代（T066-R05），
所以 `toBeVisible()` 本身证明不了失败路径，已改为断言 `data-phase="failed"`、
`flow-retry-render`（只有失败态才有）与节点/边清单的具体内容。

### 8.5 T069 的三处断言是我写错了（已改；其后在新鲜构建上实测 **7/7 通过**）

`gate5.spec.ts` 第一次实测 **4 passed / 3 failed**。逐条复核后确认三处失败都是
**断言与设计不符**，不是产品缺陷。三处修好后，`gate5.spec.ts` 在新鲜构建上
**实测 7 passed / exit 0**（构建 `21:12:05`、最新源码 `21:05:19`，
详见证据文件第 11.12 节），因此 T069 由 `implemented` 升为 `verified`。

1. **C02/C04 的「逐字原样」断言**（`toContain('img src=x onerror')`）。
   实测的渲染结果（用临时诊断打印出的 `svg text` 结构，诊断已删除）显示屏幕文字是
   `&#60;img src=xonerror=alert(1)&#62;`：尖括号在**当时的**编译期被写成 `#60;`/`#62;`；
   净化器再把其中的 `&` 写成 `&amp;`。原子串中间的**空格本来就在**（`src=x` 与 `onerror=` 之间），
   所以「原样子串」这种断言必然失败。
   已改为断言「材料里的词仍在」（`img src=x`、`onerror=alert(1)`、`第二大行`）**并且**
   「屏幕上不得出现原样的 `<img`/`<script` 标签」。断言目标从「逐字原样」改成

### 8.6 已发现但**未修**的真实问题（如实列出）

1. **`flowOutputSchema` 不限制节点 id 的字符集**。实测：
   `flowOutputSchema.safeParse({… nodes:[{id:'n1"] --> evil["x', …}]})` 返回 **success**；
   `flowNodeIdSchema` 只约束长度（1…64 codepoints），没有任何字符集检查。
   与 `T064-C03` 用例原文「非法结构按 schema 拒绝」的字面读法不一致。
   **为什么没有改**：编译器把每个 id 映射成受控的 `N0…Nn`（实测
   `nodeIdMap={"3f1a6b0e-…":"N0","normal":"N1"}`，源码里只出现 `N0`/`N1`），
   所以 id 里的代码字符**到不了渲染层**；`tests/unit/flow-compiler.test.ts` 的
   `T064-C03` 用例断言的正是这条「编译期重映射」的防线。改 schema 会拒绝掉一批
   现有取证用例，属于扩大改动范围，按「发现实现有真缺陷先报告、最小修复」的边界留给作者决定。
2. **`T064-C03` 的验收方式不是 schema 边界**。该用例名是「非法结构按 schema 拒绝」，
   但现有断言证明的是 compiler 重映射（`nodeIdMap` + 源码里只有 `N0`/`N1`），
   没有一条断言走 `flowOutputSchema` 对恶意 id 的拒绝。这是**覆盖口径**上的缺口，
   不是功能缺口（防线真实存在，只是位置与用例措辞不同）。

#### 8.7.1 新增的畸形输入用例（`tests/browser/flow-render-security.test.ts`）


度量到的事实（真实 Chromium）：

| 输入 | 净化器输出 | 判据 |
| --- | --- | --- |
| `''` | `''` | 不抛，通过只读检查 |
| `这不是 SVG，只是一句话` | 原样文字 | 不抛；非 SVG 文本不伪装成图 |
| `<div>hello</div>` | `hello` | 容器被剥除，文字留下 |
| `<svg><text>没有闭合` | `<svg><text>没有闭合</text></svg>` | 浏览器解析器补全；仍产出一张图 |
| `<>][` | `&lt;&gt;][` | 尖括号被转义成文字 |
| 含 `\u0000` | 控制字符被替换，文字保留 | 不抛，文字长度 > 0 |
| 400 层 `<g>` 嵌套 | 被解析器截断后仍返回 SVG | 不栈溢出 |
| `<svg><p>段落</p><table>…` | HTML 被剥除 | 声明为 SVG 的输入仍保留 SVG 根 |

渲染器侧：`这不是 mermaid`、`''`、`flowchart LR\n N0["甲"] -->`、`flowchart LR\n N0["甲`
四种畸形源码**全部 reject**且理由可读，且失败后 `<body>` 下**没有** `d*` 临时节点残留；
