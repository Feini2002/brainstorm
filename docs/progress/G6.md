## 3. T070 已通过的硬性约束

- **T070-C01 完整字段**：人工锁定字段、原文、修订、**被拒绝的关系**都逐字段往返。
  夹具 `tests/helpers/backupLibrary.ts` 刻意种了这些边界（人工锁定、过期条目、
  被拒关系、来源已被删除的视图），而不是只测一条干净记录。
- **T070-C02 秘密白名单**：导出用**显式白名单列**（`BACKUP_*_COLUMNS`）而非 `SELECT *`，
  产物里没有 API Key、`settings` 行、Run 快照。这条由扫描用例**和**变异实验双重确认
  （证据文件 3.1：让导出多带一个字段就立刻红 2 条）。
- **T070-C03 一致快照**：整个读取在一个事务内完成，条目/标签/关系/视图之间的引用自洽，
  不会导出「改了一半」的库。
- **T070-C04 超限**：超过 `exportBytesMax`（20 MiB）时返回 **422 `VALIDATION`**，
  不是 500，也不产出半个包。上限值同时登记在 `reference/contracts/limits.json` 与
  `src/domain/limits.ts`，由 `npm run contracts` 比对。
- **T070-C05 中文保真**：中文与 emoji 按字节保真。
- **T070-C06 无配置依赖**：没有模型配置、没有任何 Run 也能完整导出。

## 4. T071 已通过的硬性约束

- **T071-C01 未知版本**：未来 `schemaVersion` **明确拒绝**并说明版本不支持，
  不猜测兼容——猜测兼容会把「结构可能已经变了」的数据静默灌进用户库。
- **T071-C02 重复 ID**：条目、标签、关系三类重复 UUID 全部被拒。
- **T071-C03 悬空关系**：关系的条目引用必须存在（**错误**）；视图缺来源只报**警告**
  （这是合法状态，视图可以指向已被删除的条目，T053 已确立）。
  两者区别对待由 `validateBundle` 分别判定，不是同一条规则。
- **T071-C04 非空目标**：目标库已有内容时拒绝恢复，**包括只有孤立标签**的情况
  （否则会留下一批无人引用的标签）。
- **T071-C05 大文件**：超限请求体在**流式读取阶段**就以 `BODY_TOO_LARGE` 拒绝，
  不先读进内存再判断。
- **T071-C06 只读验证**：校验不改库、不动 `datasetRevision`。这是「校验」与「恢复」
  分成两个端点的根本理由，也是它可被反复调用的前提。

## 5. T072 已通过的硬性约束

- **T072-C01 往返恢复**：导出→恢复后数据与引用完全一致，`datasetRevision` 递增。
- **T072-C02 中途失败**：事务中途报错时**全部回滚**，不留下半份数据。
  变异实验（证据文件 3.2）把 `ROLLBACK` 换成空操作后立刻红 1 条。
- **T072-C03 校验后变化**：校验通过后目标又变非空（或包哈希不符）时，
  在**事务内重新复查**并拒绝。这条防的是「校验与提交之间被别的会话插了数据」的窗口，
  因此复查必须在事务内而不是复用校验端点的结果。
- **T072-C04 秘密保持**：恢复**不导入 Run**，也**不覆盖**目标的 `settings` / `secrets`。
  目标的这两张表在恢复前后逐字节一致。
- **T072-C05 不自动整理**：恢复不触发任何模型调用。这条比「没有网络请求」更强——
  它断言不产生 Run 记录，因此连「打算调用但失败了」也排除在外。
- **T072-C06 引用 ID 保持**：视图快照、关系证据、标签位置都指向正确原文。

- **T073-C01 活跃 WAL**：有未检查点的 WAL 时脚本如实报告，不误称库已完整落盘。
- **T073-C02 目录搬迁**：文档给出的搬迁步骤与实际可搬性一致，覆盖空格与 CJK 路径。

- **T073-C04 空库误读**：空目录、路径不存在都**不**被误报为损坏（退出码 0）。

不发任何会写盘的 PRAGMA（无 `wal_checkpoint`、无 `VACUUM`）。

## 7. 本轮发现的真实缺陷（摘要）

完整现象/根因/后果/修复/回归见证据文件第 5 节。三条都不是「实现没写」，
而是「已有的东西在特定条件下会骗人」：

1. **契约守卫用例会随进度静默失效**（`tests/contracts/guard.test.ts` 的 T012-C06）。
   该用例把 `/api/export` 写死成「尚未实现」，T070 落地后前提为假、用例直接红。
   更早它写死的是 `/api/graph`，G3 实现后那句替换不再命中、用例**已经静默失效过一次**
   （用例自己的注释就记着这件事）。也就是说「实现一个契约端点」当时会同时产生
   「一条红」或「一条空转」两种结果，取决于替换是否命中。
   已改为从 `PENDING_ROUTES` **动态**挑一条仍未实现的端点，随进度自然迁移。
2. **T073 损坏库断言的机制写错了**。我最初断言 `readable: true` 且 `integrity: 'damaged'`，
   实测是 SQLite 接受打开但一查询就抛错，故 `readable: false`。已按真实机制改正，
   且**没有**退化成「damaged 或 unreadable 都接受」的松断言——那会让「脚本压根没打开文件」
   也蒙混过关。
3. **lint 残留 2 条 warning**（`flow-history.test.ts` 的无用参数与导入）。已清零，
   全仓库 `npm run lint` 现在 0 problems。

## 8. 本轮修复的测试自身缺陷（不是产品缺陷）

- **T070 超限用例写错了两处**：一是试图用**单个**条目撑过 20 MiB，撞上
  `length(captured_text) BETWEEN 1 AND 10000` 的 schema 上限；二是批量插入的
  `capture_request_id` 与夹具已有记录撞了 UNIQUE 约束。改为「多条各自合法的条目
  把**库**撑超预算」，并用独立 ID 前缀。这才是用例原文「整库超限」的意思。
- **T070 哈希用例原本是空转的**：它用 `JSON.stringify` 的 replacer 数组想打乱键序，
  但那其实是**过滤**键而不是重排，于是「键序不敏感」这条恒真。
  已换成递归反转键序的函数，并**额外断言**反转后的对象键序确实不同。
- **T071 的 harness 只有一个库**：它先用夹具把库填满，再拿这个库当「恢复目标」，
  而契约要求恢复到**空**库，于是 5 条用例在断言「非空被拒」时失败。
  已改成 `source`（导出用）与 `target`（干净目标）两个库，这才是真实恢复场景的形状。
- **T072 的证据引文不是原文子串**：夹具里的引文 `清楚地定义问题和验收结果`
  并不在种下的原文里，断言必然失败。已改为原文中的真实片段 `越需要把问题说清楚`。
  这类错误的危险在于「用夹具迁就实现」——所以改的是**引文**（对齐真实原文），
  而不是删断言。
