# Zod：优势、复用颗粒度与装配边界


## 采用结论

已选：跨边界的运行时契约。本文将上游公开能力与本项目设计分开；来源索引：S17，见 [来源登记](00_sources.md)。下述装配规则是项目要求，不表示上游库会自动替我们实现。

## 值得复用的具体优势

TypeScript 只在编译时检查程序写法，不验证模型或浏览器实际传来的 JSON。Zod 在请求、模型结果、导入文件、数据库 JSON 解码和 View 渲染前建立同一套结构约束。

## 组件怎么接入

纯 schema 放 src/domain/schemas。字符串长度采用 Unicode 码点计数辅助 refine，与 SQL length 的主要语义保持一致；不同用途有不同 schema，不能用一个全字段 Item schema 接收 PATCH 以免开放系统字段。

## 不能让车轮子替我们决定的内容

结构校验通过不表示事实为真，也不表示 relation targetId 实际存在。模型输出必须在 Zod 之后继续做 ID 集合、版本、证据、图连通性和关系方向校验。

## 输入、输出和所有权

输入 unknown，输出显式 parse 结果或字段路径错误。UI 只展示安全字段错误，不回显包含 Key 的原始输入。校验错误映射为统一 error.code，而不是把整个 Zod 对象扔给浏览器。

## 最小集成实验

每个 schema 都要有空值、错误类型、超长、未知字段、嵌套过深和不合法枚举测试。尤其测试 importance 的浮点值、NaN 在序列化后的表现、数组重复元素及 emoji 字符长度。

## 替代品与不选原因

可以用 JSON Schema 工具做类似事情，但项目已经需要 TypeScript 推导与运行时验证，Zod 足够。OpenAPI 不能代替这些业务校验。

## 依赖治理

初始化时记录包名、精确安装版本、许可文件位置、是否包含原生二进制、是否需要浏览器环境、是否可能联网。提交 package-lock.json。后续升级只允许在独立变更中进行，并重复本组件的集成实验；不允许为修复一个报错同时把所有依赖升级到 latest。

如果实现与锁定版本文档不符，应记录实际 API 与最小复现，修正对应适配层。禁止直接 fork 整个上游仓库放进本项目，再靠手工编辑 node_modules 避开错误。只有无法通过公开 API 解决且得到明确架构变更记录时，才讨论替换组件。
