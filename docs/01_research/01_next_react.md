# Next.js + React：优势、复用颗粒度与装配边界


## 采用结论

已选：应用宿主与同源本机 API。本文将上游公开能力与本项目设计分开；来源索引：S01 S02 S03 S23，见 [来源登记](00_sources.md)。下述装配规则是项目要求，不表示上游库会自动替我们实现。

## 值得复用的具体优势

Next.js 让页面、Route Handler 与 TypeScript 领域模型处在一个工程里；React 让卡片、表单、抽屉和图节点复用同一组件语言。对本项目最重要的收益不是搜索引擎优化，而是少运行一个服务、少维护一次跨域认证、少同步一套接口类型。

## 组件怎么接入

页面放 src/app，各 API 显式使用 Node runtime。src/server 的数据库与密钥模块标记 server-only。页面组件通过统一 apiClient 读取 DTO，不把服务端函数直接打包进浏览器。三个重型 Renderer 使用客户端动态导入，基础记录页面不预载图形库。

## 不能让车轮子替我们决定的内容

不能假定 dev server 默认只监听本机，也不能把 next build 当成 lint。Next.js 的静态预渲染可能在构建阶段执行模块，因此 DB 模块导入不得产生文件写入。路线参数的异步约定由锁定版本决定，初始化时用一条动态路由完成实测。

## 输入、输出和所有权

输入是浏览器请求与受控组件 props；输出是同源 JSON、页面与静态资源。领域服务不能依赖 NextRequest 才能测试，应把 HTTP 解析后纯参数传进去。

## 最小集成实验

验收先启动只有文本和一个 health route 的骨架，确认进程监听、类型检查、生产构建和真实页面导航。然后加入 SQLite，再加入外部模型。若空壳都不能 build，不允许先靠禁用 TypeScript 检查推进其他功能。

## 替代品与不选原因

Vite 加独立 Node 后端也可实现，但会多出服务编排和开发代理；这里保留 Next.js 是为了延续单工程边界，不宣称它在所有桌面知识工具中最优。

## 依赖治理

初始化时记录包名、精确安装版本、许可文件位置、是否包含原生二进制、是否需要浏览器环境、是否可能联网。提交 package-lock.json。后续升级只允许在独立变更中进行，并重复本组件的集成实验；不允许为修复一个报错同时把所有依赖升级到 latest。

如果实现与锁定版本文档不符，应记录实际 API 与最小复现，修正对应适配层。禁止直接 fork 整个上游仓库放进本项目，再靠手工编辑 node_modules 避开错误。只有无法通过公开 API 解决且得到明确架构变更记录时，才讨论替换组件。
