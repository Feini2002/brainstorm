# Vitest + Playwright：优势、复用颗粒度与装配边界


## 采用结论

已选：确定性测试与浏览器验收。本文将上游公开能力与本项目设计分开；来源索引：S19 S20，见 [来源登记](00_sources.md)。下述装配规则是项目要求，不表示上游库会自动替我们实现。

## 值得复用的具体优势

Vitest 覆盖领域函数、SQL Repository、模型协议和编译器；Playwright 覆盖按钮、路由、图表生命周期、键盘操作和本机安全接口。它们验证的是不同层次，不能只跑其中一种就宣布完整可用。

## 组件怎么接入

Vitest 使用临时数据库与可注入 transport，测试默认不访问真实模型。Playwright 单独安装 Chromium，启动隔离数据目录的应用实例；测试替身只通过测试环境依赖注入启用，不暴露在正式 Settings。

## 不能让车轮子替我们决定的内容

测试替身能证明程序分支正确，不能证明具体外部模型的语义效果。浏览器截图也不能证明数据库已经持久保存或密钥没有出现在响应里，因此断言需要包含网络与存储观察。

## 输入、输出和所有权

输入固定 fixture 与故障模式；输出断言、报告和失败定位。每个报告要区分执行通过、执行失败、环境阻塞、未执行，不能写一个笼统的“全部已自检”。

## 最小集成实验

验收至少包含无 Key CRUD、真实文件重启、无关系图、模型超时、重复提交、版本冲突、导出无秘密和空库恢复。浏览器依赖下载失败要给出明确操作，不跳过后把结果记成通过。

## 替代品与不选原因

测试开发依赖是允许的工程工具，不属于产品过度架构。禁止依赖过多的规则不能成为没有自动化验证的理由。

## 依赖治理

初始化时记录包名、精确安装版本、许可文件位置、是否包含原生二进制、是否需要浏览器环境、是否可能联网。提交 package-lock.json。后续升级只允许在独立变更中进行，并重复本组件的集成实验；不允许为修复一个报错同时把所有依赖升级到 latest。

如果实现与锁定版本文档不符，应记录实际 API 与最小复现，修正对应适配层。禁止直接 fork 整个上游仓库放进本项目，再靠手工编辑 node_modules 避开错误。只有无法通过公开 API 解决且得到明确架构变更记录时，才讨论替换组件。
