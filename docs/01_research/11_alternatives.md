# 完整产品、编辑器与图形库：为什么不能混为一谈


## 一、分类决定拼法

完整产品带有自己的数据模型、配置、生命周期和界面。可嵌入组件只解决一个局部问题。算法库甚至没有界面。把这三类都叫“车轮子”容易产生错误期待：安装一个图形库不会得到知识整理能力，部署一个笔记产品也不会自动让它和另一个画布共用实体 ID。

AFFiNE、Memos 属于可直接使用或深度二次开发的完整产品；BlockSuite 属于编辑器与协同工具栈；React Flow 和 Excalidraw 是交互图形组件方向；Dagre 是布局算法；Markmap 是层级转换与展示；Mermaid 是声明式图语言与 Renderer。相关来源见 S08—S15、S27—S31。

## 二、为什么不基于 AFFiNE 整体 fork

AFFiNE 的文档与画布融合思路值得参考，但整体 fork 会让 MVP 同时面对它的工程组织、块模型、构建依赖和可能的服务端功能。当前产品只有短文本与几个只读投影，继承完整应用的复杂性没有对应收益。

不 fork 并不意味着重新写它已有的编辑器。这里直接减少编辑器需求，让 textarea 成为真实且充分的第一版输入端。等用户确实需要图片、嵌入内容和结构化块，再按数据迁移成本评估 BlockSuite 或其他编辑器。

## 三、为什么不让 Memos 负责采集

Memos 很适合快速记录，但让它负责采集而本系统负责知识处理，需要解决双向同步、删除传播、ID 对齐、权限与来源回跳。若第一天就做两个本地应用，用户仍要面对“到底在哪个地方编辑”的问题。

本 MVP 只借鉴无标题输入、时间线和快速保存。未来用户已有大量 Memos 内容时，优先实现一次性导入或明确单向同步，再考虑实时双向同步。禁止把两个数据库都称为主库。

## 四、为什么推迟自由白板

Excalidraw 与 tldraw 的自由画布能力很强，但本需求最初是让碎片思路被组织和观察，不是画任意形状。自由白板需要新增形状生命周期、选区、撤销、粘贴、资源管理与卡片引用边界，这些功能会把范围从知识碎片 MVP 推向通用设计工具。

tldraw 的当前许可需要单独核验生产使用条件，不能沿用过去宽松许可的印象；本版因此不采用它。Excalidraw 可以在后续成为独立 canvas 类型，但必须保存引用 Item 的形状数据，而不是复制成断开的文字。（来源 S30、S32。）

## 五、为什么不用 Sigma 起步

Sigma 面向图网络可视化的优势与 React 节点卡片的需求不同。第一版想点击一个节点就打开原文、审核关系和编辑标签，React Flow 的 React 组件模型更直接。未来若实际图规模与性能测试证明 DOM 节点成为瓶颈，再评估 Sigma，并保留同样的 GraphData 契约。（来源 S08、S31。）

## 六、没有选中的技术不属于失败

向量数据库、RAG 框架、Agent 框架、CRDT 和消息队列各自有适用场景，但当前没有需要它们解决的已验证瓶颈。延后是为了把首版验证问题收窄到“记录是否容易、整理是否可信、多视图是否有用”，不是否认它们未来的价值。

扩展必须由可观察信号触发：字面召回连续漏掉有价值旧知识才引入语义索引；多设备需求真实出现才讨论同步；用户确实在画布上反复手动排版才引入自由白板。不要用未来想象倒逼现在维护所有能力。
