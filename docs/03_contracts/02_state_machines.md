# 状态机、并发和失败恢复的唯一约定


## 一、Item 状态

raw 表示存在原文而没有当前版本的成功整理。processing 表示最新整理运行仍有效。done 表示当前原文已成功整理。error 表示最近一次整理失败且没有可宣称为当前成功的结果。stale 表示有旧结果，但它基于旧原文或与最新人工编辑发生冲突。

状态不决定原文是否存在。只要采集提交成功，rawText 就必须可读。用户修改 done 条目的 rawText，rawVersion 与 revision 同时增加，状态转 stale。用户修改标题时仅 revision 增加，并锁定该字段；它不意味着原文语义变化，但进行中的 AI 运行应检测到冲突，避免覆盖人工工作。

运行开始时保存原有状态与快照。成功提交使状态 done，清理可读错误；失败时若有旧成功结果则保留它并标明失败提示，状态由当前原文与整理基础版本比较确定，精确优先级见《DTO、身份、版本与规范化》，不能把原文或旧摘要清空。实现时通过统一 deriveItemStatus helper 决定，禁止各页面自写不同规则。

## 二、Run 状态

running 只能进入 succeeded、failed、interrupted、conflict，四个终态不能再次进入 running。用户重试是新的 requestKey 和新的 Run，而不是把旧记录改回运行中。对同一个 requestKey 的重复请求返回原 Run：完成时返回已存在结果，运行时返回 202 与 runId，失败时返回原错误而不重新计费。

failed 指模型网络、协议、验证或本地提交失败。interrupted 指超过租约期限仍无提交，或显式恢复逻辑确认运行无法继续。conflict 指模型生成期间目标版本、配置关联规则或来源集合不再满足提交条件。用户已经删除目标时也不得让旧响应重建记录。

终态写入采用条件更新：只有 state=running 且 inputHash 匹配才能提交。运行恢复程序与迟到的模型响应竞争时，数据库只能接受一方。若恢复已经置 interrupted，迟到响应必须丢弃；不能把它偷偷变回 succeeded。

## 三、期限与重试

单次提供者请求默认四十五秒，整次操作绝对期限一百二十秒，运行租约一百八十秒。三者解决不同问题：请求超时控制一次网络等待，操作期限覆盖可能的一次结构修复，租约给中断恢复留出判断空间。具体值来自 limits.json，测试必须使用可注入时钟缩短等待。

默认不自动重试付费网络请求。401、403、404、429、5xx、超时和连接断开都返回明确错误，让用户决定是否再试。只有收到完整响应但 JSON 结构不合法时，允许在同一次操作中做最多一次结构修复；UI 和 Run 记录必须显示实际尝试次数，不能隐藏额外请求。

结构修复只修复格式和字段，不扩展事实，不引入新候选 ID，不变更用户意图。总期限到了就停止，即使还没用完修复次数。用户再次点击 Retry 会生成新的 Run，并明确告知模型调用可能产生费用。

## 四、两个标签页

设置、条目与视图保存都需要 expectedRevision。两个标签页基于同一版本编辑，先保存者成功，后保存者收到 409，并保留自己的草稿以便比较。不能采用最后写入者无提示覆盖，尤其不能覆盖 Key 配置和人工修正的摘要。

Graph 的位置拖动也按 View revision 保存。页面内可以合并短时间多个位置更新，但真正提交必须带基准版本；冲突时提示重新载入布局，不把别人的布局变化扩散到领域数据。

## 五、刷新与页面切换

用户保存成功后即使立刻刷新，也能通过 Item ID 重新读取。AI 请求正在执行时刷新，旧浏览器可能断开请求，服务端是否继续取决于运行时；系统不作后台完成保证。新页面读取有效 Run 并显示状态，过期后提供“重新整理”入口。

轮询不是完成任务的引擎。GET Run 只能读取状态；过期清理使用受保护的 POST 或运行注册前的维护步骤，不得悄悄启动模型。页面隐藏暂停轮询，重新可见再读取；终态立即停止。全站没有每秒查询所有条目的逻辑。

## 六、数据库事务切点

采集事务包含插入 Item、标签关系和 datasetRevision；整理注册事务包含唯一 Run 占用与 processing 标记；整理提交事务包含版本检查、受允许字段更新、关系 upsert、datasetRevision 与 Run 成功；导入事务包含全量数据恢复。

任何事务内部都不能有 fetch、定时器等待、浏览器渲染或文件下载。事务失败以后必须 rollback；错误处理再使用新事务写安全错误，不能在已经失败的事务上继续执行。

SQLite busy 超时只是并发防护，不是把同步数据库变成无限吞吐。MVP 单进程和短事务是前提。负载测试应验证在持续整理时仍能保存新笔记，且不会因等待模型而锁住数据库。
