# 关系词典、审核行为与证据门槛


## 1. 先建立有限词典

similar_to 是两条表达在主要内容上相似，不代表二者互为支持证据；related_to 是主题或关注对象存在明确联系，但不足以归为更强关系；contradicts 是针对相同条件或主张出现不一致，不把不同场景的结论简单对立。这三种是对称关系，持久化按ID排序端点，展示无需箭头。

extends 表示 A 在 B 的讨论基础上增加条件、范围或解释；supports 表示 A 为 B 提供理由或例证，不表示B已被证明；example_of 表示 A 是 B 概念的具体例子；depends_on 表示 A 的成立或实施依赖 B；causes 表示 A 引起 B 的因果主张。后五种保留方向，UI必须用自然语言准确解释，不能全部画“相关”箭头后丢失含义。

每种强关系都有误用风险：先后出现不是causes，属于同一个话题不是supports，分支展开不是depends_on。LLM可以返回零条关系。不能在最终验收要求“这三句话必须至少连一条”，因为网络模型输出不稳定且无关资料不应被强制连接。自动化结构验收使用已知响应替身，真实语义验收由人检查质量。

## 2. 审核优先于分数

origin=ai 的新关系进入 suggested。用户 accept 后成为 accepted，score仍是模型当时的评分，不因点击认可自动改为1.0。用户reject后保留同一记录为rejected，默认图不显示，但重新整理查到相同规范键必须尊重拒绝。只有用户明确restoreSuggestion才能恢复建议。

origin=manual 的关系是用户直接声明，reviewStatus固定accepted、score=null。同样端点类型的AI记录可以被人工创建动作升级成manual，保留必要旧信息的安全摘要，不复制成第二条平行边。用户不再认可人工关系时删除即可，不能强行设置rejected违反数据约束。

accepted也不是经过外部事实核查的“真关系”，它是用户知识库内认可的关联。产品文案使用“已确认/待确认/已拒绝”，避免“真实/虚假”二元标签。关联评分0.89不能解释为89%正确概率；不提供基于评分的伪统计质量指标。

## 3. 证据检查的能力边界

模型生成关系至少提供一条目标原文quote和一条候选原文quote，各不超过一百二十码点。每条quote必须是相应当前rawText的连续子串，且对于候选必须来自实际发送片段。服务器检查itemId在允许集合内、quote非空、版本未变化，拒绝编造引号。

逐字匹配证明“引用存在”，不证明“关系逻辑必然成立”。因此字段校验通过仍只是建议。模型用两句真实文字拼出错误因果依然可能发生，用户审核与保守类型选择才是进一步约束。文档不能把Zod和字符串匹配描述成语义真实性证明器。

当对称关系交换端点时，sourceRawVersion和targetRawVersion必须一起交换，evidence内部itemId不变。不要只交换ID而留错版本。端点版本改变后关系stale，默认新图推导排除；历史图仍可显示它当时存在，但提示当前材料已经变化。

## 4. 因果图的额外门槛

Flow AST中的kind='causal'要求relationIds至少包含一条当前accepted、未过期、type='causes'的Relation，且它的端点落在对应源节点与目标节点的itemIds中。仅有模型自述或两条相似笔记不满足机器门槛。无此依据时输出hypothesis，并用明确文字标为“推测/建议顺序”。

这比组织普通关系更保守：用户可以先审核或人工建立cause关系，再让流程投影使用；也可以直接接受一张明确标注为假设的探索图。程序不把假设边反写为知识库causes，防止一次生成让未证实关系变成下一次生成的“证据”。

sequence只表示材料中描述的步骤顺序，association表示联系，dependency可以引用已确认depends_on。它们的文字同样不能冒充事实证明；缺少明确依据的新增排列一律hypothesis。边类型不由CSS颜色决定，而由canonical数据决定，导出时也保留假设标签。

## 5. 拒绝、删除和再生成

建议关系的隐藏用reject，视图里的边隐藏仅是当前视图过滤，删除知识条目则会级联删除端点关系。这三个动作完全不同，必须有不同文案。用户不能因为想“让画面简单”而无意删除原文。

重新整理时已accepted或manual关系不被模型覆盖reason/score；已rejected不复活；仍suggested的相同关系允许以当前依据更新，但若用户恰在审核需revision保护。新模型建议与人工边方向不同可分别存在，因为它们是不同规范键；界面若造成语义冲突应展示，不擅自删除人工判断。

知识条目删除导致历史View来源缺失，不让View里的标签重新生成一个笔记“补洞”。撤销删除不做MVP通用回收站；删除确认明确不可直接撤销，恢复依赖备份。不要做半个软删除系统让查询和外键语义不一致。
