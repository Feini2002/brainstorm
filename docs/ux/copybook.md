# 文案手册（T082）


本文件是 T082 的交付物之一，记录**用户可见中文的现行约定**。它不是设计稿，也不是愿望清单：每一条都对应代码里的一个真实位置，改文案时以这里的定义为准，新增文案时在这里登记。

任务的权威规则见 [T082 实施规格](../04_tasks/G6/T082_ux_quality.md) 的 R01–R06；验收场景见 [T082 用例](../05_tests/G6/T082_cases.md)。

## 一、词表：四个动作必须分开（R01）

保存、整理、生成、审核是四件不同的事，用户看到的动词必须能区分它们。这四个词的唯一出处是 `src/features/shared/StatusLabel.tsx` 的 `ACTIONS`，其它文件不得再写一遍字面量。

| 词 | 含义 | 谁落盘/发请求 | 典型入口 |
| --- | --- | --- | --- |
| 保存 | 原文写入本机数据库 | 只写 SQLite，不发模型请求 | 收件箱「只保存」、Ctrl+Enter |
| 整理 | 模型为已保存的原文生成结构化字段 | 发一次模型请求，写回 `knowledge_items` | 收件箱「保存并整理」、详情抽屉「重新整理」 |
| 生成 | 用选中材料创建一张视图（脑图/流程图） | 发一次模型请求，写 `views` 行 | 脑图页「生成脑图」、流程图页「生成」 |
| 审核 | 人工判断一条关系成立与否 | 只改变 `review_status`，不碰模型 | 关系列表「确认」「拒绝」、详情面板 |

代码位置：

- `ACTIONS` / `waitingLabel` / `waitingFor`：唯一的动词与进行时措辞（`正在保存…`、`正在整理…`）。
- `failureKeepingSaved(action, reason)`：失败时先说已完成的部分（`原文已保存，但整理没完成：…`），再说恢复方式。调用方传的是 `ACTIONS.organize`，因此这句永远不会把「整理失败」写成「保存失败」。

## 二、已知的历史混用，及其处理

| 曾经的说法 | 问题 | 现在的说法 |
| --- | --- | --- |
| 保存 / 整理 混用 | 「保存失败」被用来描述整理失败，用户会以为原文丢了（T025-R04 明令禁止） | `原文已保存，但整理没完成：…` |
| 「加载中」（`LoadingIndicator` 默认值） | 六个页面所有等待都用同一句，读屏用户无法分辨在等什么 | `label` 现在是必填项，且必须写清动作（见第四节） |
| 「依据过期」 | 读起来像日期到了，不像证据变了；也和「会话已过期」撞词 | 「依据已变化」（见第三节） |

## 三、评分与新鲜度（R02）

**score 一律称「关联评分」。** 它是模型判断的两条记录相关强度，不是正确率、置信度或概率（`docs/03_contracts/01_data_contract.md`、`docs/03_contracts/08_relations_and_evidence.md`）。唯一出处是 `StatusLabel.tsx` 的 `SCORE_LABEL` 与 `SCORE_DISCLAIMER`（「模型判断的关联强度，不是正确率」）；`features/graph/badges.ts` 的 `describeScore` 与 `RelationReviewPanel` 都从这里取词。

人工关系没有评分。这一点必须说出来，而不是渲染成 `0.00` 或 `1.0`：

- 人工：`人工建立，没有模型评分`
- 模型没给分：`本次模型没有给出评分`
- 有分：`关联评分 0.82（模型判断的关联强度，不是正确率）`

**stale 一律称「依据已变化」，不称「数据损坏」。** 含义是：当前整理结果基于旧版本的原文，动作是重新整理。出处是 `src/domain/staleness.ts` 的 `STALE_LABEL` / `STALE_HINT`（`依据已变化，需重新整理`），`StatusLabel.tsx` 再导出给组件层。

三个状态必须分开写，因为它们对应三种不同的动作：

| 状态 | 措辞 | 依据 | 用户动作 |
| --- | --- | --- | --- |
| 依据已变化 | `依据已变化` | 来源原文的 `rawVersion` 变过 | 重新整理 / 重新生成 |
| 来源已删除 | `来源已删除` | 来源条目不存在了 | 无法恢复；旧视图保留原样 |
| 会话已过期 | `本地会话已过期，请刷新页面` | 进程重启后令牌轮换 | 刷新页面 |

禁止的写法：把 stale 说成「数据损坏」「文件坏了」「内容错误」。原文改过不等于数据坏了，这样写会让用户不敢再编辑（T082-C02 的「必须排除」项）。

## 四、等待、空数据、无关系、无 Key、失败（R03）

`LoadingIndicator` 的 `label` 必填，且必须说明**在等哪个动作**。现状清单：

| 位置 | label |
| --- | --- |
| 资料库搜索 | `正在搜索` |
| 收件箱最近记录 | `正在读取最近记录` |
| 详情抽屉 | `正在读取这条记录` |
| 关系面板 | `正在读取关系` |
| 来源列表 | `正在读取这张视图的来源` |
| 脑图渲染 | `正在渲染脑图` |
| 流程图渲染 | `正在渲染流程图` |
| 关系图画布（动态加载） | `正在加载关系图画布` |
| 关系图读取 | `正在读取关系图` |
| 生成流程视图 | `正在生成流程视图` |
| 备份校验 | `正在校验备份` |
| 保存 | `正在保存…`（`SavePhaseStatus`） |

「正在…」的省略号由 `LoadingIndicator` 统一追加，调用方不自己写标点。

空态与无关系态分别设计（`StatusLabel.tsx` 的 `EMPTY_STATES`）：

| 场景 | 文案 |
| --- | --- |
| 一条记录都没有 | `还没有任何记录。在收件箱写一句就会出现在这里，没有模型也可以保存原文。` |
| 有记录但筛选没匹配 | `没有匹配的记录。换个关键字，或清除筛选条件。` |
| 条目没有任何关系 | `这条记录还没有关系。可以在详情里建立人工关系，或运行整理让模型给出建议。` |
| 还没选材料 | `还没有选中材料。先在资料库或收件箱勾选要整理的内容，再从选择条进入这里。` |

无 Key 是最容易被写成「应用不可用」的一处，因此拆成两句（`NO_MODEL_HINT` + `MODEL_REQUIRED_FOR`），设置页与收件箱提示共用：

- 设置页 `settings-model-required-for`：`「保存并整理」、生成脑图和生成流程图需要先在设置里配置模型。`
- 设置页 `settings-model-optional`：`还没有配置模型连接。保存原文、搜索、编辑、删除、人工关系和已保存的视图都不需要模型，照常可用。`
- 收件箱 `capture-hint`：`整理需要先在设置里配置模型；这条原文仍会照常保存，离线功能不受影响。`

失败文案的形状固定为「先说完成了什么 → 再说没完成什么 → 再说怎么办」。唯一出口是 `failureKeepingSaved`。

## 五、危险动作必须说明范围（R05）

三处不可撤销的操作各自有唯一的措辞，集中在 `StatusLabel.tsx` 的 `DANGER_SCOPE`：

| 动作 | 说明的效果 | 说明的不影响 | 组件 |
| --- | --- | --- | --- |
| 删条目 | 原文与整理结果都会被删除，无法撤销；相关关系一并删除 | 已经保存的视图不会被删除，但会提示依据已变化 | `DeleteItemDialog`（`delete-item-scope`） |
| 删视图 | 只会删除这个视图 | 知识条目、标签与关系都不受影响，原文仍然在资料库里 | `DeleteViewDialog`（`delete-view-scope`） |
| 删 Key | 只会删除保存的 Key | 知识条目、标签、关系和已保存的视图都不受影响，离线记录照常可用 | `LlmSettingsForm` |
| 从备份恢复 | 只能恢复到空知识库；已有内容时服务端直接拒绝，不合并、不覆盖 | 不触发整理，也不带回 Key | `BackupPanel` |

两个确认框的焦点策略是**故意相反**的，并且是可用性要求而不只是风格：

- `DeleteItemDialog` 把焦点放在「确认删除」上：用户是在抽屉里做了删除决定之后才看到这个框，框是最后一步。
- `DeleteViewDialog` 把焦点放在「取消」上：删视图的入口在用户正在浏览的列表旁边，一个本来要按「打开」的 Enter 不能把视图删掉。

两条说明都必须**同时**出现，不能只写「确定删除？」——那样两个操作看起来一样，用户要在事后才知道差别。

## 六、术语与上下文限定词

| 用 | 不用 | 原因 |
| --- | --- | --- |
| 视图 / 脑图 / 流程图 / 关系图 | 图表（泛称） | 「图表」分不清是哪种投影，删除确认框里会说不清删的是什么 |
| 知识条目 / 记录 / 原文 | 数据、文档 | 「原文」是用户自己写下的东西，删除时必须点名它 |
| 关联评分 | 分数、置信度、正确率 | 见第三节 |
| 依据已变化 | 过期、失效 | 见第三节 |
| 人工建立 / 模型建议 | 用户关系 / AI 关系 | 出处类型是用户能看懂的两个来源 |

「图表」在 `SourceList`、`DeleteItemDialog` 等处曾用来指代脑图，已改为「视图」，因为同一个组件同时服务脑图和流程图。

## 七、改文案时的检查清单

1. 改动是否落在 `StatusLabel.tsx` 已有的词表里？能复用就不要新写字面量。
2. 是否把「保存」和「整理」写成了同一件事？失败文案必须说出原文还在。
3. 是否把 score 说成了正确率，或把 stale 说成了数据损坏？
4. `LoadingIndicator` 的 label 是否指明了具体动作？
5. 危险动作是否写清了「影响什么」和「不影响什么」？
6. 同一个词是否在别处有第二种写法？`rg -n '旧词' src tests` 确认没有漏改。
7. 改完跑 `npx tsc --noEmit && npx eslint src --max-warnings=0`，并跑 `npx playwright test tests/e2e/a11y-and-copy.spec.ts`。
